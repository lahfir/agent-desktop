agent-desktop reads Linux apps through AT-SPI over D-Bus. The loop, refs, JSON envelope, sessions, and traces match every platform, so this page covers only what differs on Linux. GNOME is the measured desktop; X11 and Wayland sessions both work and differ in input, capture, and window control. The examples on this page ran on an X11 session (Xvfb with the openbox window manager, no GNOME Shell), so shell surfaces and notifications were not exercised.

## Requirements

- Ubuntu 24.04 or later on x86_64 or aarch64, with a glibc 2.35 floor. Other distributions need an `at-spi2-core` bridge with fix (commit `dc0dc33`); Ubuntu 22.04's bridge aborts on `Action.GetActions`.
- A graphical session of the signed-in user, a running AT-SPI bus (`at-spi2-core`), and a window manager. Run agent-desktop from a shell inside that session: the session bus, display, and runtime directory come from its environment. A TTY login, an SSH shell without those variables, a container without a bus, or another user's session sees no apps.
- X11 keys need XTEST. Wayland keys need GNOME Mutter RemoteDesktop, or KWin's EIS input service with `libxkbcommon` on KDE Plasma. The Wayland clipboard needs `wl-clipboard`.
- On X11, `clipboard-set` needs `agent-desktop-linux-clipboard-owner` beside the binary. npm installs and release archives include it; from source, build it with `cargo build --release -p agent-desktop-linux --bins`.
- A private state root. A group-writable or world-readable `~/.agent-desktop` makes commands that write there fail with `INTERNAL`. Run `chmod 700` on it, or let agent-desktop create it.

## Check the accessibility bus

Linux has no permission dialog for accessibility; whether the bus answers gates everything. Run `status` first:

```bash
agent-desktop status
```

```json
{
  "permissions": {
    "accessibility": { "state": "granted" },
    "automation": { "state": "not_required" },
    "screen_recording": { "state": "not_required" }
  },
  "platform": "linux",
  "supported_surfaces": ["window", "sheet", "alert", "menu"]
}
```

An unavailable bus has four usual causes, each reported with the raw D-Bus error in `platform_detail`:

- **No session bus.** Run inside a desktop session, or start one with `dbus-run-session -- COMMAND`.
- **AT-SPI not installed.** Install `at-spi2-core`. For Flatpak add `--talk-name=org.a11y.Bus`; for snap connect `desktop-legacy` or `unity7`.
- **Launcher cannot start.** Read `systemctl --user status at-spi-dbus-bus.service`.
- **Socket gone.** Restart `at-spi-dbus-bus.service`, or log out and back in.

Judge health with `status`, not with `busctl`: on a cold session `org.a11y.Bus` has no owner until its first use. Do not restart a bus you did not start, because other clients on a shared host depend on it.

## What works headless

Ref actions are semantic AT-SPI calls that never move the pointer or change the active window. Under `--headed` on X11, `click`, `right-click`, and `type` try physical input first and fall back to the semantic action only after a `not_delivered` refusal. See [Headed mode](/desktop/guides/headed-mode).

## App naming

`--app` takes the name `list-apps` prints, such as `gnome-calculator`, or a desktop-entry name or id backed by a verified executable, such as `Files`. It never matches a window title.

```json
{ "bundle_id": "org.gnome.Calculator", "name": "gnome-calculator", "pid": 8255, "presentation": "foreground", "process_instance": "6d91df60:28340" }
```

`list-windows --app` is an exact, case-insensitive match; `list-apps --app` also matches a substring. Window ids are opaque strings such as `w-1.11-org-gnome-Calculator-a11y-...`, valid for the life of the window's process. Several instances of one app share a name; pick one with `--window-id`. `launch` accepts an absolute path, a desktop id, a bare command, or a desktop entry name.

## Surfaces

`supported_surfaces` lists `window`, `sheet`, `alert`, and `menu`, plus GNOME Shell kinds the session can resolve. After an opener, read `data.surfaces`. A GTK popover appears asynchronously, so if it is absent, run `wait --menu` before you assume the opener failed. A list-backed GTK4 dropdown is part of the window tree, not a menu surface. See [Surfaces](/desktop/surfaces).

## Chromium, Qt, and Electron

An app appears in `list-apps` only when its toolkit registered on the accessibility bus.

<table>
  <thead>
    <tr><th>App</th><th>Needs</th></tr>
  </thead>
  <tbody>
    <tr><td>GTK3, GTK4</td><td>Nothing. An app that started before the bus never registers: restart it</td></tr>
    <tr><td>Qt</td><td><code>QT_ACCESSIBILITY=1</code> in its environment</td></tr>
    <tr><td>Chromium browsers</td><td><code>--force-renderer-accessibility</code>; in a bare session without a settings daemon, also <code>--env ACCESSIBILITY_ENABLED=1</code> on <code>launch</code></td></tr>
    <tr><td>Electron</td><td>No flag. <code>--no-sandbox</code> where <code>chrome-sandbox</code> is not setuid</td></tr>
  </tbody>
</table>

```bash
agent-desktop launch google-chrome --arg=--force-renderer-accessibility
```

To drive the web contents with agent-browser instead, launch the app with `--cdp`; see [Chromium and Electron apps](/desktop/guides/chromium-and-electron). GTK apps nest deeply with unnamed `group` wrappers that `-i --compact` keeps; read past them, or let a skeleton find the drill targets. Electron native dialogs are not on the AT-SPI tree.
